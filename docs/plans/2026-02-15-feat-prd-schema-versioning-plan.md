# PRD Schema Versioning

## Overview

Add a `schema_version` field to PRD files to enable backward-compatible schema evolution. This allows future versions of Burlaki to handle PRD files from different schema versions with proper validation and migration.

## Problem Statement

**Current state:** PRD files have a `version` field (set to `1`) that is:
- Never validated
- Unclear whether it's schema version or project version
- Not used for migration or compatibility checking

**Why this matters:**
- v0.3.0 (Learning System) and v0.4.0 (Parallel Execution) will add new PRD fields
- Without schema versioning, detecting incompatible PRDs is impossible
- Migration debt accumulates as schema evolves

## Proposed Solution

Add `schema_version` field using Semantic Versioning:

```json
{
  "schema_version": "1.0.0",
  "version": "1.0",
  "created": "2026-02-15T10:00:00Z",
  "plan": "...",
  "stories": [...]
}
```

**Version semantics:**
- **MAJOR**: Breaking changes (field renames, required field additions)
- **MINOR**: Additive changes (new optional fields)
- **PATCH**: Bug fixes in schema validation

## Technical Approach

### Lazy Migration

Detect old PRDs and add `schema_version` on first read:

```bash
# In burlaki-continue, burlaki-run, etc.
SCHEMA_VERSION=$(jq -r '.schema_version // empty' .agents/tasks/prd.json)

if [ -z "$SCHEMA_VERSION" ]; then
  # Old PRD - migrate to v1.0.0
  jq '. + {schema_version: "1.0.0"}' .agents/tasks/prd.json > .agents/tasks/prd.json.tmp
  mv .agents/tasks/prd.json.tmp .agents/tasks/prd.json
  echo "Migrated PRD to schema_version 1.0.0"
fi
```

**Why lazy migration:**
- No upfront migration script needed
- PRDs are migrated as they're accessed
- Zero impact on existing workflows

## Future Considerations

- Additive changes (new optional fields) → increment minor version (e.g., `1.1.0`)
- Breaking changes (field renames) → create explicit migration command
